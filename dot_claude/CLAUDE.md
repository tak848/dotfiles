# user による指示

プロジェクト横断のユーザー指示です。

## 調べてから書く

版の差異・設定や API の使い方・新機能・知識のカットオフ以降の話は、記憶ではなく一次ソース（公式ドキュメント・リポジトリのソース・リリースノート）で確かめてから書く。確かめられなかったことは「未確認」と書き、推測を事実の形で書かない。ユーザーはこちらの回答を前提に作業を進めるので、裏付けの無い断定はそのまま手戻りになる。知らない記法が実際には正しく動いていることも、リポジトリ固有の規約もあるので、自分の知識だけで「間違っている」「存在しない」「非推奨」と断定しない。リポジトリ内を読めば分かること、一般的なプログラミングの知識、この会話で確定した事実は調べ直さなくてよい。

依存・ツール・設定を足すときは、版も書き方もその場で調べる（記憶にあるものは古いことが多い）。最新の安定版を使い（古い版に留めるなら理由をコメントに書く）、既知の脆弱性を確認し、checksum・署名・commit SHA・digest で固定できる形にする。検証の無い `curl | sh` は足さない。トークンや権限は必要最小限にし、秘密情報をコード・ログ・コマンドラインに出さない。

Web ページの本文を忠実に読みたいときは `defuddle parse <url> --md` を使う。`WebFetch` は本文を小型モデルで要約してから返すので、細部が落ちたり変わったりする（軽い事実確認ならそれでよい）。`defuddle` は JS のレンダリングが要るページでは本文が取れないので、そのときは `WebFetch` か claude-in-chrome を使う。

## 進め方

データのスキーマ（DB・API・proto）とアーキテクチャの決定は、ユーザーのレビューを経てから進める。それ以外のやり直せる作業は聞かずに進め、結果で報告する。不可逆な操作と外に出る操作は、リポジトリの規約や指示で許されていなければ確認する。

作業時間・手間・間に合うかどうかの見積もりを、頼まれていないのに出さない。それを理由に範囲を縮めたり、後のリリースに回す・別の PR に分ける選択肢を自分から持ち出したりしない。期限があるなら間に合わせる前提で進め、障害は事実として伝えて解消に動く。リリースをずらすかはユーザーが決める。こちらの見積もりは人間が手で作業する前提の人月の感覚で、実際より何倍も長く出る（10 分の作業を 1 時間、1 日の作業を 2 週間と言う）ため。

subagent には積極的に委譲してよい（Claude Code の既定は控えめにするよう求めるが、このユーザーは常時許可している）。委譲したら待つだけにせず自分の作業を進め、context の不足や脱線に気づいたらその時点で介入する。成果物の品質に責任を持つのは委譲した側なので、結論に効く部分は自分で確かめる。model は基本は指定せず既定を使う。指示があれば `sonnet` や `haiku` も使ってよい。

## ユーザーに届く text

tool の結果を受けた後、次の tool を呼ぶ前に書いた text は、要約されてユーザーに届かないことがある。確実に届くのは、ターン最後の text と tool の入力だけ。

- 調査結果・判断の根拠・報告は、ターン最後の text に書く
- 質問は AskUserQuestion で行う。判断材料を先に見せるときは、判断材料を text に書いて最終行を装飾なしの `質問予告: <問いの要約>` にし、その応答には tool 呼び出しを含めない。その後、text を書かずに AskUserQuestion を呼ぶ。判断材料は question や選択肢の説明に詰め込まない
- ExitPlanMode の変更点や、却下への応答は plan 本文に書く
- 話が噛み合わないときは、途中の text が届いていない可能性を考え、ターン最後の text で出し直す

構成・before/after・選択肢の比較のように文字だけでは伝わりにくい判断は、先に HTML の説明ページを作り、その環境で使える共有の手段（artifact など）で出してリンクを渡す。長い md より図と表のある HTML の方が読まれるため。plan mode の中でも作ってよい（止めるべきは実装の編集で、説明用の HTML は含まれない。許可の判定は permission hook に任せる）。

## GitHub

GitHub の操作は `gh` で行う。

- PR のコメントは、PR 本体のコメントとレビューコメントのスレッドの両方を見る（API が別で、片方だけでは取りこぼす）
- レビューの指摘を直したら、そのコメントに返信し、直した commit へのリンクを付ける。レビュアーがどこで直ったかを追えるようにするため
- issue や PR へのコメント・返信の末尾に `(by Claude Code)` を付ける。読み手が AI の書いたものだと分かるようにするため
- PR はリポジトリの PR テンプレートの構成で書き、作ったら full URL を示す
- PR の本文を書き換えるときは、先に今の本文を取得し、bot が足したコメントやバッジを残す。手元の文面で丸ごと置き換えると消える
- public のリポジトリの commit・PR・コメントには、公開されていない情報（社内のリポジトリ名・パス・仕組みなど）を書かない

## 置き場所

- 一時ファイルは `z/` に置いてよい（global の git ignore 済み）。名前に `date` で取った日時を入れると整理しやすい（例: `YYYYMMDDhhmm-hoge.md`）
- プロジェクトに還元すべき規約・知見はそのプロジェクトの `CLAUDE.md`（Codex は `AGENTS.md`）、個人的なもの（進め方・好み）は `CLAUDE.local.md` に置く。`CLAUDE.local.md` に書く前にユーザーに確認する。auto-memory は使わない

## ファイルの末尾

ファイルを編集したら、末尾が改行で終わるようにする。Git の差分に「No newline at end of file」が出ないようにするため。

## 散文の改行

PR 本文・plan・issue や PR のコメント・ドキュメントなどの散文では、改行を段落・リスト・コードブロックの区切りにだけ使い、1 文の途中で折り返さない。GitHub では改行がそのまま表示に出て読みにくくなり、Markdown ファイルでは文を直すたびに折り返し位置がずれて差分が膨らむため。

## 技術用語を直訳の漢語にしない

英語の概念を、日本語で慣用されていない漢語に置き換えない。canonical を「正典」、wiring を「配線」、happy path を「幸福経路」、時間やトークンの上限を指す budget を「予算」とするたぐい。読み手は元の英語を復元してから意味を取ることになり、語義も本来より狭く伝わる。次の順で選ぶ。

1. その分野で慣用されている日本語があればそれを使う（wiring は「繋ぎ込み」、happy path は「正常系」、canonical form は「正規形」、canonical な参照先は「SSoT」、time budget は「制限時間」「タイムアウト」、token budget は「上限」。「予算」は金額の予算にだけ使う）
2. 無ければ、日常的に口にされているカタカナ語・英語で書く（ボイラープレート、スロットリング、エッジケース）
3. どちらも据わりが悪ければ、普通の言い方で説明する（「どれを正とするか」「どこで差し込むか」）

迷ったら、その語を同僚に口頭で言うかを考える。言わない語は書かない。原語をカタカナに置き換えただけの語（「キャノニカル」など）も、口にしないなら同じく避ける。
