# user による指示

プロジェクト横断のユーザー指示です。

## 調べてから書く

記憶にある知識は古かったり、細部が違っていたりする。次のどれかに触れる回答は、一次ソースで確かめてから書く。確かめられなかったことは「未確認」と書き、推測を事実の形で書かない。ユーザーはこちらの回答を前提に作業を進めるので、裏付けの無い断定はそのまま手戻りになる。

- ライブラリ・フレームワークのバージョン差異
- 設定方法や API の使い方
- 新機能や最新のベストプラクティス
- 知識のカットオフ以降の情報

一次ソースは、公式ドキュメント・リポジトリのソース・リリースノート。WebFetch / `defuddle`（後述）、GitHub MCP / `gh` で直接読む。ライブラリのドキュメントを引くときは context7 も使える。リポジトリ内を読めば分かること、一般的なプログラミングの知識、既にこの会話で確定した事実は調べ直さなくてよい。

知らない記法や構文が実際には正しく動いていることがあり、リポジトリ固有の規約もある。API やオプションは非推奨になったり新しく増えたりする。自分の知識だけで「間違っている」「存在しない」「非推奨」と断定せず、確かめてから言う。

## 依存・ツール・設定を書き足すとき

ライブラリ・ツール・言語ランタイム・GitHub Actions の action・コンテナイメージなどの版や、設定・API の書き方は、記憶ではなくその場で調べて書く。記憶にある版や書き方は古いことが多い。

- 版は、リリース・パッケージレジストリ・公式ドキュメント（例: `mise latest`、`gh release view`）で最新の安定版を調べて使う。古い版に留める理由があるときは、その理由をコメントに書く
- 書き方は、使う版の公式ドキュメントにある現在の記法・推奨 API に合わせる
- 版を選ぶときは既知の脆弱性・アドバイザリを確認する。取得するものは checksum・署名・commit SHA・digest で検証・固定できる形にし、検証の無い `curl | sh` のような取得と実行は足さない。トークンや権限は必要最小限にし、秘密情報をコード・ログ・コマンドラインに出さない

## GitHub

GitHub の操作は GitHub MCP（`mcp__plugin_github_github__*`）でも `gh` でもよい。

- PR のコメントを確認するときは、PR 本体のコメントとレビューコメントのスレッドの両方を見る。取得する API が別で、片方だけでは取りこぼす（GitHub MCP なら `pull_request_read` の `get_comments` と `get_review_comments`）
- GitHub MCP の `body` に改行を入れるときは、実際の改行文字を使う。リテラルの `\n` はエスケープされて文字のまま残る
- レビューコメントの指摘を直したら、そのコメントに返信し、直した commit へのリンク（`https://github.com/{owner}/{repo}/commit/{sha}`）を付ける。レビュアーがどこで直ったかを追えるようにするため
- issue や PR にコメント・返信するときは、本文の末尾に `(by Claude Code)` を付ける。読み手が AI の書いたものだと分かるようにするため
- PR を作るときは、リポジトリの PR テンプレート（ルート、`.github/`、`docs/`、各 `PULL_REQUEST_TEMPLATE/` の下）を探し、見つかればその構成で書く
- PR を作ったら、full URL（`https://github.com/{owner}/{repo}/pull/{number}`）を示す
- PR の description を書き換えるときは、先に現在の description を取得し、bot が挿入したコメントやバッジ（Devin review badge、Greptile のコメントなど）を残したまま編集する。手元の文面で丸ごと置き換えると、それらが消える

## Web ページ本文の取得

`WebFetch` は取得した本文を小型モデル（reported: Haiku）で要約してから返すので、通常の HTML ページでは本文が要約・改変されて忠実さが落ちる。ページ本文を忠実に全文読みたいときは `defuddle parse <url> --md` を使う（モデルを挟まず、整った Markdown が返る）。

レスポンスが既に markdown（`text/markdown` かつ ~100K 文字未満。約 80 の信頼ドメインが典型）のときは、`WebFetch` もモデルを通さず原文を返すので、そのままでよい。軽い事実確認やピンポイントの Q&A も `WebFetch` でよい。`defuddle` は静的 HTML をパースするので、JS のレンダリングが要る SPA では本文が取れない。その場合は `WebFetch` か claude-in-chrome を使う。

## 一時ファイルの置き場所

一時的なファイルは `z` ディレクトリに置ける（`.config/git/ignore` で ignore 済み）。ファイル名に日時を入れると整理しやすい（例: `YYYYMMDDhhmm-hoge.md`）。日時は `date` コマンドで取得する。

## ファイルの末尾

ファイルを編集したら、末尾が改行で終わるようにする。Git の差分に「No newline at end of file」が出ず、POSIX のテキストファイルとして扱えるため。

## Python の実行

Python は `uv run` で実行し、`python` / `python3` を直接呼ばない。システムの Python はプロジェクトの依存を持たず、管理もされていないため。`uv run` は毎回許可が要るので、許可済みのツール（`awk`、`jq`、シェルスクリプトなど）で済むならそちらを使う。

## subagent への委譲

subagent には積極的に委譲してよい。Claude Code の既定の指示は委譲を控えめにするよう求めるが、このユーザーは常時許可している（この指示がその許可にあたる）。独立して並行できる作業から投げ、委譲したら待つだけにせず自分の作業を進める。context の不足や脱線に気づいたら、その時点で介入する。

委譲しても、成果物の品質に責任を持つのは委譲した側。subagent の報告をそのまま結論にせず、結論に効く部分は自分で該当箇所を確かめる。確かめていないことは「未確認」と書く。

model は指定せず、セッションの既定モデルを使う。ごく軽い作業に限り `sonnet` を指定してよい。`haiku` は指定しない。

## ユーザーに届く text

tool の結果を受けた後、次の tool を呼ぶ前に書いた text は、要約されて原文がユーザーに届かないことがある。確実に届くのは、ターン最後の text と tool の入力だけ。

- 調査結果・判断の根拠・報告は、ターン最後の text に書く
- 質問は AskUserQuestion で行う。判断材料を先に見せるときは、判断材料を text に書いて最終行を装飾なしの `質問予告: <問いの要約>` にし、その応答には tool 呼び出しを含めない。その後、text を書かずに AskUserQuestion を呼ぶ。判断材料は question や選択肢の説明に詰め込まない
- ExitPlanMode の変更点や、却下への応答は plan 本文に書く
- ユーザーとの話が噛み合わないときは、途中の text が届いていない可能性を考え、ターン最後の text で出し直す

## Git

`git switch`、`git restore`、`git commit`（`--amend` を除く）は確認なしで実行できる。`--amend`、`--no-gpg-sign`、`reset --hard` は使わない。履歴の書き換え、署名の省略、未 commit の作業の消失につながるため。

## 学びや規約の置き場所

Claude Code の auto-memory（`~/.claude/projects/<project>/memory/`）は設定で無効にしてあるので使わない。学び・規約・コンテキストは、内容に応じて次に置く。

- プロジェクトに還元すべき規約・知見は、各 agent が読める位置に置いてプロジェクトで git 管理する。Claude はそのプロジェクトの `CLAUDE.md`（リポジトリ直下か該当サブディレクトリ）、Codex はそのプロジェクトの `AGENTS.md`
- 複数人で共有する意味のないもの（タスクの進め方、細かい運用ルール、個人の好みに近い話）は `CLAUDE.local.md` に書く。git worktree では worktree root の `CLAUDE.local.md`。書く前にユーザーに確認する

## 散文の改行

PR 本文・plan・issue や PR のコメント・ドキュメントなどの散文では、改行を段落の区切り・リスト・コードブロックなど意味のある区切りにだけ使い、1 文の途中で折り返さない。GitHub の issue・PR・discussion では改行がそのまま表示に出て読みにくくなり、Markdown ファイルでは文を直すたびに折り返し位置がずれて差分が膨らむため。

## 技術用語を直訳の漢語にしない

英語の概念を、日本語で慣用されていない漢語に置き換えない。canonical を「正典」、wiring を「配線」、happy path を「幸福経路」、時間やトークンの上限を指す budget を「予算」とするたぐい。読み手は元の英語を復元してから意味を取ることになり、語義も本来より狭く伝わる。次の順で選ぶ。

1. その分野で慣用されている日本語があればそれを使う（wiring は「繋ぎ込み」、happy path は「正常系」、canonical form は「正規形」、canonical な参照先は「SSoT」、time budget は「制限時間」「タイムアウト」、token budget は「上限」。「予算」は金額の予算にだけ使う）
2. 無ければ、日常的に口にされているカタカナ語・英語で書く（ボイラープレート、スロットリング、エッジケース）
3. どちらも据わりが悪ければ、普通の言い方で説明する（「どれを正とするか」「どこで差し込むか」）

迷ったら、その語を同僚に口頭で言うかを考える。言わない語は書かない。原語をカタカナに置き換えただけの語（「キャノニカル」など）も、口にしないなら同じく避ける。
